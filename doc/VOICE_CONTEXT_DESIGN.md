# Voice context carryover — design (for review, nothing built)

**Status:** proposal only. No migrations applied, no workflows imported, no app changes.
**Date:** 2026-10-27
**Author:** Hermes (design responding to "can the assistant bring in the context of the last conversation when the app starts or resumes?")

---

## 1. What already works, so we build only the missing part

| Layer | State | Where |
|---|---|---|
| App shows the last conversation on launch | **Works** | `session_persistence.dart` restores chat id + transcript; `AgentScreen._restoreTranscript()` |
| Assistant remembers the **text** thread | **Works** | every `/webhook/chat` call carries the persisted `chatId`; Vapi keeps the thread |
| Assistant remembers the **voice** conversation | **Missing** | a new call starts with company variables only; nothing stores what was said |

Nothing about the app needs to change for this feature. It is a server-side capture + inject job.

---

## 2. Findings from investigating the live stack (all verified today)

1. **The assistant's `serverUrl` is `https://n8n2.ordrnow.com/webhook/vapi/assistant-hook`** and `serverMessages` is **unset**.
   Vapi's documented default set is `conversation-update, end-of-call-report, function-call, hang, speech-update, status-update, tool-calls, transfer-destination-request, handoff-destination-request, user-interrupted, assistant.started`.
   → **Vapi is already POSTing every call's `end-of-call-report` to our hook — and the hook ignores it.**

2. **Evidence of the volume:** the "Vapi Assistant Hook" workflow ran **1,398 times in the last 7 days** (execution_entity, read from the live n8n SQLite). The app only invokes that hook once per call start, so the overwhelming majority are Vapi event POSTs, each running a Postgres query + variables builder and returning a JSON the event doesn't use.

3. **No conversation storage exists:** `db/` ends at `0038_invoice_templates_verify.sql`; there is no calls/messages/conversation table anywhere.

4. **`analysisPlan` is unset on the assistant** → reports carry `artifact.transcript` and `artifact.messages`, but no `analysis.summary`. A summary has to be enabled (or derived) if we want compact context.

5. **Report payload shape** (Vapi docs, server events): `{ message: { type, endedReason, call, artifact: { transcript, messages[], recording } } }`.

6. **A legacy, unrelated live workflow also exists**: "end of call report" (`K5h8akMdXeLXkI2K`, webhook `/webhook/callreport`, Twilio SMS + Google Sheets CRM upsert, created 2026-07-13, 3 runs/7d). It is **not** wired to this assistant's `serverUrl`. Do not confuse it with the new path, and do not extend it.

Consequence: the capture half is nearly free — the data is already arriving. The work is to (a) stop discarding it, (b) store it, (c) inject a compact form of it at the next call start.

## 3. Architecture

```
call start (app)                     call end (Vapi)
      |                                    |
      v                                    v
 POST /webhook/vapi/assistant-hook    POST /webhook/vapi/assistant-hook
   (direct from the app,               (Vapi server message:
    X-User-Token)                       type = end-of-call-report)
      |                                    |
      +--> resolve company                 +--> branch on message.type
      +--> INSERT voice_calls               +--> upsert transcript + summary
           (pending, call_ref)              +--> status = 'reported'
      +--> SELECT last reported row
      +--> respond assistantOverrides
           { variableValues: {…, recent_context} }
```

Single webhook path, two branches. Calling `POST /webhook/vapi/assistant-hook` from the app is unaffected by `serverMessages` (that setting only governs Vapi→server sends).

## 4. Data model — `db/0039_voice_context.sql` + `db/0040_voice_context_verify.sql`

```sql
CREATE TABLE IF NOT EXISTS voice_calls (
  id               bigserial PRIMARY KEY,
  company_id       integer NOT NULL REFERENCES company_profile(id) ON DELETE CASCADE,
  call_ref         uuid NOT NULL,
  vapi_call_id     text UNIQUE,
  status           text NOT NULL DEFAULT 'pending'
                     CHECK (status IN ('pending','reported','abandoned')),
  started_at       timestamptz NOT NULL DEFAULT now(),
  ended_at         timestamptz,
  ended_reason     text,
  duration_seconds numeric(10,2),
  summary          text,
  transcript       text,
  messages         jsonb,
  cost             numeric(12,6),
  created_at       timestamptz NOT NULL DEFAULT now(),
  updated_at       timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX IF NOT EXISTS voice_calls_ref_key    ON voice_calls (call_ref);
CREATE INDEX        IF NOT EXISTS voice_calls_recent_idx ON voice_calls (company_id, ended_at DESC NULLS LAST);
```

- `call_ref` is generated by the hook (uuid v4) at call start and is the join key between "a call is about to happen" and "here is its report".
- Register `0039`/`0040` in `deploy/migrate.sh` in DEPLOY order (after the 0037/0038 pair), and regenerate `doc/SCHEMA.md` afterwards.
- Verify file: insert a pending row + a reported row, assert the unique index rejects a duplicate `call_ref`, assert the CHECK rejects a bogus status, assert the FK rejects `company_id = 9999`, then ROLLBACK.

## 5. Capture path (workflow changes)

**5.1 Branch the hook.** In `vapi-assistant-hook.json`, immediately after the webhook node, add a Switch/IF on `{{ $json.body.message.type }}`:

- `end-of-call-report` → report branch (new nodes, below)
- anything else (including the app's direct call, which has no `message.type`) → today's variables path, unchanged.

**5.2 Report branch nodes** (new; ids from a plain counter, per the n8n id pitfall):

1. `Extract Call Report` (Code): pull `vapi_call_id = message.call.id`, `ended_reason = message.endedReason`, `started_at/ended_at` from `message.call`, `transcript = message.artifact.transcript`, `messages = message.artifact.messages`, `cost = message.cost`, `summary = message.analysis?.summary ?? null`; derive `duration_seconds`.
2. `Exec: match_or_insert_call` (Postgres, `operation: executeQuery`): resolve the target row —
   `call_ref` from `message.call.assistantOverrides.variableValues.call_ref` **if present** (must be confirmed on a real payload, see T1), else the most recent `pending` row for the resolved company within 6 h.
   Then `UPDATE … SET status='reported', vapi_call_id=…, ended_at=…, … RETURNING id`.
   If no pending row matches (e.g. a call started from another device), `INSERT` a `reported` row with company = the resolved company and `call_ref = gen_random_uuid()`, tagged in `ended_reason` prefix `unmatched:` — so the gap is visible rather than silent.
3. `Respond Report (ok)` (Respond to Webhook, 200 `{"ok":true}`) — Vapi expects no body for this type.

**5.3 Dedupe & re-delivery.** `vapi_call_id UNIQUE` + `ON CONFLICT (vapi_call_id) DO UPDATE` makes a retried report idempotent.

**5.4 Orphan cleanup.** A nightly SQL step (piggyback on an existing daily job) flips `pending` rows older than 6 h to `abandoned` — a call that never connected must not be injected as "last conversation".

**5.5 Narrow `serverMessages` (optional but recommended, same change).**
Set `serverMessages: ["end-of-call-report", "tool-calls"]` on the assistant (`backend/vapi_assistant.json` + `python3 backend/create_vapi_assistant.py`).
This removes `conversation-update`, `speech-update`, `status-update`, `assistant.started` etc. — the source of the ~1,390 wasted runs/week — while keeping the two messages we actually act on.
**Must be verified**: `python3 qa/verify_vapi_tools.py` (every tool carries its own `server.url`) plus one live voice tool call end-to-end, because a tool inheriting the assistant-level `serverUrl` would depend on this list.

## 6. Injection path

**6.1 Query in the hook** (new Postgres node, guaranteed row — a 0-row result ends the chain silently):

```sql
WITH last AS (
  SELECT summary, transcript, ended_at, ended_reason
  FROM voice_calls
  WHERE company_id = $1
    AND status = 'reported'
    AND ended_at > now() - interval '7 days'
    AND ended_at < now() - interval '30 seconds'
  ORDER BY ended_at DESC
  LIMIT 1
)
SELECT left(coalesce(summary, transcript), 1200) AS recent_context,
       ended_at, ended_reason
FROM last
UNION ALL
SELECT NULL, NULL, NULL
WHERE NOT EXISTS (SELECT 1 FROM last);
```

**6.2 `Build Hook Variables`** adds to the returned `variableValues`:

```json
"recent_context": "Last call: 2026-10-27 15:10 PDT, ended by user.\nSummary: <…≤1200 chars…>"
```

Absent/empty when there is no recent reported call — the prompt section must handle both cases.

**6.3 System prompt section** (new, in `backend/vapi_assistant.json`):

```
## Recent context
variableValues.recent_context may hold a summary of the last voice conversation.
Use it to avoid re-asking things the PM already told you, and to offer continuity when
they return to the same topic. Never read it aloud, and never state a fact from it as
current without checking a tool first — amounts, balances and statuses change.
If the last call ended mid-task and they resume it, pick up from there instead of
starting over. If it is empty, behave exactly as today.
```

**6.4 Greeting.** v1 keeps today's deterministic greeting. An optional later variation ("Back to it? Last time we were on INV-0004") is a product decision, not part of this build (see open question 2).

**6.5 Failure isolation.** The context lookup runs after the company resolution and before the variables response; any error or timeout must fall through to the variables response **without** `recent_context`. The hook must stay fast — the app is waiting on it to start the call.

## 7. What could go wrong, and the guarantee against it

| Failure | Guarantee |
|---|---|
| Report never arrives (Vapi outage, very short call) | row stays `pending` → `abandoned` after 6 h; nothing injected |
| Report arrives twice | `ON CONFLICT (vapi_call_id)` upsert |
| Report arrives before the pending row commits | upsert inserts the row; `call_ref` fallback via company+time window |
| Two calls for one company | `call_ref` disambiguates; report matching prefers the explicit ref |
| Context table is empty / query fails | guaranteed-row query + null-safe builder; hook returns today's payload |
| Transcript enormous | stored, but only `left(coalesce(summary, transcript),1200)` is injected |
| Stale facts mislead the model | prompt rule: context is a hint, tools are truth |
| serverMessages narrowing breaks a tool | `qa/verify_vapi_tools.py` + one live voice tool call before release |

## 8. Retention & privacy

- Transcripts are customer business data. Default retention **90 days**, enforced by a nightly `DELETE FROM voice_calls WHERE ended_at < now() - interval '90 days'` (verified by a row-count assertion).
- `summary` may be kept longer than `transcript` if the user wants; that is open question 1.
- No recording URLs are stored in v1 (audio is not needed for context).

## 9. Tasks, each with its test plan

Order is dependency order. Nothing proceeds without an explicit go.

**T1 — Capture the current reality (read-only).**
Read one real `end-of-call-report` payload from an n8n execution of the hook and answer three questions: does `message.type` arrive as expected, **is `assistantOverrides.variableValues` echoed back in `message.call`**, and what is the real transcript size.
*Test:* print the payload's top-level keys + the variableValues presence boolean for one real call; recorded in this doc's appendix. This decides whether matching uses `call_ref` or the company+time fallback.

**T2 — Schema.**
`db/0039_voice_context.sql`, `db/0040_voice_context_verify.sql`, register both in `deploy/migrate.sh`.
*Test:* hermetic run in migrate.sh order on a scratch Postgres; live run after a `pg_dump` pre-snapshot; the verify file asserts insert/unique/check/FK and rolls back; `doc/SCHEMA.md` regenerated and diffed.

**T3 — Hook: branch + pending row + report handler.**
Restructure `vapi-assistant-hook.json` with a type switch, a `pending` insert, and the report upsert.
*Test:* offline node harness with four fixtures (app variables POST, end-of-call-report POST, tool-calls POST, malformed POST) asserting: response bodies by branch, SQL param arity/order, and that the variables branch is byte-identical to today for non-report bodies. `node --check` on every generated jsCode. Unique node ids and connection integrity validated before import.

**T4 — `serverMessages` narrowing.**
*Test:* `python3 qa/verify_vapi_tools.py` green (32/32 carry `server.url`), one live voice tool call returns a real result, and execution counts for the hook drop from ~200/day to ≈ 1 per call + tool calls (measured over the next 24 h).

**T5 — Injection.**
Context query + `recent_context` in `Build Hook Variables` + the prompt section.
*Test:* harness fixtures — no rows, one fresh row, one stale (>7 d) row, 20 KB transcript (assert ≤1200 chars injected), query-error path (assert the variables response still returns without `recent_context`). Live: `POST /webhook/vapi/assistant-hook` with a real `X-User-Token` and assert `recent_context` appears in the JSON.

**T6 — Live end-to-end.**
Place a short real call, say one identifying sentence, hang up. Then:
1. assert exactly one `voice_calls` row `status='reported'` with non-null `transcript` and `ended_reason`;
2. `POST` the hook with the token → `recent_context` contains the sentence's topic;
3. start a second call and ask "what were we just talking about?" → assert from the **second call's stored transcript** that the assistant used it (not from hearing it).
*Test:* the three assertions above, plus a `SELECT` showing both rows.

**T7 — Retention job.**
Nightly SQL (abandon + 90-day delete) wired into an existing daily workflow or a cron SQL.
*Test:* insert a 91-day-old row and a 2-day-old pending row, run the job, assert exactly the expected deletions.

**T8 — Documentation.**
`doc/SCHEMA.md` regen, `doc/NEXT_STEPS.md` entry, project skill note (the "reports already arrive and were being discarded" fact is worth keeping).

## 10. Rollout and rollback

- Deploy as ONE script (the established pattern): pre-dump → 0039/0040 → import both changed workflows → activate → container restart → `create_vapi_assistant.py` → probes (T5 live + one real call report) → SCHEMA regen.
- **Rollback:** re-import the previous workflow JSONs (repo history), restore `serverMessages` by re-running `create_vapi_assistant.py` from the parent commit, and leave the table in place but unused (dropping it destroys the only transcripts — decide at the time).

## 12. Non-goals (explicitly out of scope)

- Re-attaching to a live call, or fixing the "Start Voice enabled during a live call" state bug (separate problem, reverted feature).
- Vector memory / search over old transcripts ("what did we say in August about Oakridge") — this is last-call continuity only.
- Any change to the Flutter app, and therefore any APK rebuild.
- Cross-company or cross-user memory: one user per company, company-scoped rows.
